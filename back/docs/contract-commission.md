# 合同销售与交付提成

## 操作入口

1. 财务与回款管理 → 提成核算 → 提成规则，维护公司确认的首单/续单制度。系统不自动绑定规则或设置真实比例。
2. 生效合同详情 → 提成与业绩，或提成核算 → 合同业绩，选择规则、交付结算条件，填写销售人员份额及依据，保存并确认。
3. 财务确认实际到账后，销售按合同净回款核算，不要求招聘入职，也无需将销售收入分摊给候选人。
4. 交付选择入职模式时，在招聘业绩归属中确认交付人员；选择服务验收时，在合同提成中登记验收日期、收费条款、真实凭据及交付人员。随后在业绩明细分摊实际到账。
5. 生成月度差额 → `submitConfiguredAction('submit')` 走现有按钮流程 → 纳入专属提成工资 → 核税、工资审批、实际付款。员工“我的提成”只显示本人进度及发放记录。

## 金额口径

- 合同金额只用于预计，实际按确认的到账扣除关联原到账的已确认退款及冲销计提；不自动扣除收入中的税额或业务成本。
- 合同净回款 × 总提成率形成唯一提成池，保留两位小数，再拆销售和交付预算。销售按销售部门内份额分配，满足回款条件即可核算。
- 交付预算在所有成果及未分摊余额间按分摊净回款统一分配尾差，再按个人份额分配。招聘人数不会放大合同预算。
- 入职交付按规则的首期比例释放，保证期明确完成后释放尾款；验收交付释放对应已分摊预算。交付退款、替换等异常沿用原有暂缓和扣回逻辑。
- 回款、退款、交付条件或分摊变化后生成新差额，不改写批准历史。同一笔收入不重复计提，原工资发放与个税控制保持生效。

例如净回款 1,999 元，总提成率 50%，销售占池的 30%，则池 999.50 元、销售 299.85 元、交付 699.65 元；该例仅说明计算，不代表公司制度。

## 权限与兼容

- 复用提成核算模块 341410 的规则、归属、分摊、核算、提交、审批和工资按钮权限与客户数据范围。合同模块 341201 可查看合同提成，变更仍需提成归属权限。本人查询仅需个人薪资模块 341006，返回本人金额。
- 规则及销售人员确认后冻结；停用规则只影响未来选用，交付继承已冻结规则。归属保存、确认及验收登记均保留审计记录。
- 存量 `source_type=application`、无 `parent_id` 的招聘归属保持原算法，阻止再叠加合同销售归属。不得批量把旧归属转换为新合同模式，否则可能重复计提。
- 新合同销售记录 `source_type=contract`、`contract_source_id=合同ID` 唯一；交付记录通过 `parent_id` 引用销售主记录，验收来源为 `acceptance`。沿用既有批次、明细、审批和工资表。

## 部署

- H2：启动时在 `commission.sql` 后自动执行 `commission-contract.sql`，放宽候选人/职位非空约束并新增合同来源字段；不会创建任何真实销售归属或回款。
- 存量 MySQL 8：备份后执行 `back/db/mysql/commission-contract-upgrade.sql`，再部署并重启后端。脚本保留历史，可重复执行。
- 新 MySQL：使用生成的 `back/db/mysql/umm_oa.sql`。执行 `node back/tools/build-mysql-sql.mjs` 可重新生成。
- 集成测试使用内存 H2，覆盖无入职销售核算、分次回款、退款、交付分段、验收、预算及尾差、历史兼容、本人数据和工资衔接。
